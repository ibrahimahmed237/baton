# B2: Codex adapter

Built on fixtures only. No real Codex chat, database or process was read, written or started. Not yet run live.

## What was built

The Codex adapter in `baton/adapters/codex/`, one class per job as in B1. Every path comes from a `root` argument that stands for the home folder (`root/.codex/...`); the process controls and the command launcher are injected.

- **Locator.** Chats are the `threads` rows of `state_5.sqlite`: id, name (else title), folder (`cwd`), updated time. Archived rows, rows without a rollout, sub-agent rows (`thread_source = 'subagent'`, a non-empty `agent_role`, or `source` containing "subagent") are not listed. A row whose rollout is missing or outside the root does not exist for Baton.
- **Reader.** Extended with a `CodexReader` class: `read`, `usage` (last `token_count`: `last_token_usage.total_tokens`, `model_context_window`, `rate_limits`; the limit counts as reached from `used_percent >= 100` or `rate_limit_reached_type`, and ends once its `resets_at` has passed), `files_changed` (edit-style tools and `apply_patch` patches, also inside a shell call). TOOL_TEXT, a missing call id and an unknown time survive the write/read round trip (marker fields, below).
- **State.** Held = the thread's lock file exists and a shared `flock` on it fails. Replying = held and the newest task event is a `task_started` (`task_complete` and `turn_aborted` close it). Format = the `threads` columns are the checked set and no column Baton cannot fill is required, and the newest three rollouts hold only known record types (`session_meta`, `response_item`, `event_msg`, `turn_context`, `compacted`). Version string `state_5`.
- **Writer.** `add`: next ordinals, the six-record turn shape from `spike/m0_append.py`, then the four timestamp columns. `create`: rollout file (exclusive create, fsync), strict parse and read-back check, then the `threads` row in one transaction, then a resolve check; any failure puts the earlier steps back. `rename`: `title` and `name`. `cut`, `place`, `restore`: `NotAvailable` (after the format check, so an unknown format reports `UnknownFormat` first, as the shared suite demands). `prepare` saves a durable pre-write receipt; the intent manifest in `root/.baton-rollback/<token>.json` is fsynced before the first change. `take_back` works from a fresh process, and refuses with `ChatChanged` if anything Baton wrote has been changed since (reverse-order rule), `ChatHeld`/`ChatReplying` if Codex holds the chat, and `NotAvailable` when it would shorten a rollout that Codex's chat view has read past.
- **Hooks.** `hooks.json` entries for `UserPromptSubmit` and `Stop` (merged beside other entries; an unreadable file is never overwritten). `check` reports installed (note `setup.hooks`), installed but not trusted (`setup.trust_once`), or ready; it only reads `config.toml`. Turn-end prints exactly `{}`.
- **Runner.** `[<bundled codex>, "exec", "--ephemeral", "-s", "read-only", "--", prompt]` with the folder as working directory, through an injected launcher. `available` needs the binary and `login status` to succeed. Never `resume`, refuses `read_only=False`.
- **App.** `open` = `codex://threads/<id>` (id checked to be plain characters) or the app itself; `close` refuses while a held chat is replying, then asks the app to quit and waits up to 10 s; `release` = `NotAvailable`. The real process calls (`ps`, `open`, `osascript`) are in `SystemProcess` and are never reached in tests.

## Decisions where the plan was silent

1. **Replying needs held.** The plan says "a task has started without a completion after it". Read literally, a chat that crashed mid-task would block closing the app for ever. A rollout nobody holds is not replying. Held chats are refused by `add` anyway.
2. **Order of refusals:** unknown format, then missing chat, then `ChatReplying`, then `ChatHeld`. Same order as B1. `place` and `cut` check only the format first.
3. **Rename of a held chat raises `ChatHeld`** (the suite requires an error with the chat open and the app running; Codex only shows the name after a relaunch anyway). Rename of an unheld chat is allowed while the app runs.
4. **Taking back a create** deletes the row and the file even if Codex's chat view has read the new chat, provided nobody holds it and nothing was added. Codex's index is never edited (orphaned index rows for a missing thread are assumed harmless). Only taking back an *add* is gated by the index offset.
5. **Index cannot be read** (table or columns not found) counts as "read past": `NotAvailable`, nothing changed.
6. **Verification failures raise `ChatChanged`** (no better domain error exists; `domain/errors.py` untouched).
7. **Times:** a time the source turn did not have is written as the write time in the record, with `batonAtUnknown: true`, and read back as empty. Codex never sees an empty timestamp.
8. **Create copies** sandbox policy, approval mode, model, effort and CLI version from the newest user chat and `base_instructions` from the first of the five newest that has them (as `spike/m0_create.py`). With no chat to copy: `{"type":"read-only"}`, `on-request`, no instructions (the same fallback `reference/codex-claude-session-sync` uses). No state database at all: `NotAvailable`, and no database is ever created.
9. **`has_user_event = 0`** on created threads, exactly as the spike inserted them (the spike's AT_ONCE measurement was made with it).
10. **Tool calls** are written as `function_call` / `function_call_output` so the shared round trip holds, although `replays_tool_calls` is false and the mapping service should flatten them first. `is_error` of a result is not kept.
11. **Format scan cost:** the global format check looks at the first three rollouts by `updated_at_ms`, only their last 1 MB, ignoring a line still being written; the target chat of an `add` is checked in full and strictly.
12. **Limit end:** a reached limit whose `resets_at` is in the past is reported as not reached. When reached, `limit_resets_at` is the latest reset among the full windows (the weekly one when only it is full); when nothing is reached it is `None`.
13. **Hook output when there is nothing to attach** is `{}` (not empty), because Codex is strict about hook output.
14. **Sessions folder** uses local time for the date and file name, as Codex names them.

## Where the fixture may not match the real Codex (check in the live run)

1. `threads`: column names are from `spike/m0_create.py` (27 columns) plus `agent_role` (seen in the third-party `reference/` tool). Types, NOT NULL and defaults are guesses; the real table has other columns I have not seen. If a real column is NOT NULL without a default, the adapter reports an unknown format and refuses to create (safe, but would turn writing off).
2. `thread_history_1.sqlite`: table names are from the spike; columns (`thread_id`, `next_byte_offset`, `next_ordinal`) are **guessed**. The adapter looks for a column named `thread_id`/`id` and one containing "offset"; if it finds neither it refuses to take a write back. The live run must show whether "read past" is detected correctly.
3. **Hook trust storage.** The spike says trust is per entry but not where it is kept. I read `config.toml` for `[hooks.state."<hooks.json path>:<event>:..."]` with a `trusted_hash` (a guess). If wrong, `check` never reports ready (safe: it keeps asking for the one-time trust). `hooks.json` is assumed to have Claude's shape (`hooks.<Event>[].hooks[].{type,command}`), at `~/.codex/hooks.json`. The spike used a project-level file.
4. **Marker fields** `batonMessageKind`, `batonOriginalCallId`, `batonAtUnknown` are added at the top level of a record, next to `ordinal`. Unknown whether any Codex version rejects unknown top-level keys.
5. **`id` on written response items** (message, function_call, function_call_output). The spike wrote no ids; the reader needs them to keep turn ids stable across a round trip. Real Codex has to accept and keep them.
6. `token_count` shape: `info.last_token_usage.total_tokens`, `info.model_context_window`, `rate_limits.{primary,secondary}.{used_percent,resets_at}` (epoch seconds), `rate_limit_reached_type`. Values of `rate_limit_reached_type` are unknown; any non-empty value counts as reached.
7. **Lock check.** `flock(LOCK_SH | LOCK_NB)` on `thread-writer-locks/<id>.lock`, as the spike. If Codex took its lock in the instant between our check and release it could momentarily fail to lock; a held chat could also be taken just after our last check (the check is repeated right before the first byte).
8. `thread_source` values: only `'user'` is listed and used as a template; other values for legitimate chats would be missed.
9. The known record types are the five listed above; a real rollout with another type makes writing stop (reading continues).
10. `codex login status` exists; the bundled CLI path is `/Applications/ChatGPT.app/Contents/Resources/codex-cli/CodexCLI.app/Contents/MacOS/codex`; `exec` may need `--skip-git-repo-check` in a folder that is not a git repository (not added, the plan names the three flags only).
11. App process path `/ChatGPT.app/Contents/MacOS/ChatGPT` and `osascript ... tell application "ChatGPT" to quit`.

## Open questions

1. Is a created chat allowed to inherit the user's newest thread's sandbox policy (possibly full access)? Done as the spike did; a stricter default would be a change to what the user sees.
2. Should taking back a create refuse when Codex's index has already read the new chat? Chosen: no (decision 4).
3. A `place`/`cut`/`restore` call raises `NotAvailable` even from `prepare`; services must check `facts.can_cut` first (they do for undo).
4. Where does Codex really keep hook trust (item 3 above)? If it is not readable, C4/`setup` may want to record that the user confirmed trust.
