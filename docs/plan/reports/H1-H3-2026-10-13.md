## H1 — an unfinished task is a reply, held or not

**Changed**
- `baton/adapters/codex/state.py:98` `replying()` returns `unfinished_task(path)` only; it no longer needs `held()`.
- `baton/adapters/codex/state.py:112` new `replying_chats()`: ids in the adapter's scope (original plus created) whose newest task event is a start.
- `baton/adapters/codex/app.py:86` new `_require_nothing_replying()`, used twice in `close()` (before and inside `global_idle`, lines 96 and 101). It keeps the old refusal for a held chat outside the scope (NotAvailable, without reading its rollout) and then refuses with `ChatReplying` when any scoped chat has an unfinished task, held or not. Before this, only held chats were scanned, so the app could be quit with an unheld unfinished task.

**Callers checked**
- `writer._check` asks `replying` before `held`, so a held and replying chat gives `ChatReplying`, a held idle chat `ChatHeld`. Unchanged order.
- `state.condition()` now reports `replying=True, open=False` for an unheld unfinished task. Services already test `replying` before `open` (`journal.check_write`, linker, merger, undo, brief, read views), so the note is `relaunch.replying` ahead of `write.chat_open`.
- `ChatReplying.note_id` is `relaunch.replying`, which exists in the catalogue. The tests assert the refusal's note id is in `CATALOGUE`. No catalogue change.

**Tests**
- `tests/adapters/test_codex.py:491` `test_unfinished_task_in_a_chat_nobody_holds_still_counts_as_replying_and_is_not_written_to` replaces the old test that asserted the opposite. It checks `open=False, replying=True`, `replying_chats()`, `add` and `rename` raise `ChatReplying`, bytes and row unchanged, no rollback folder, note in catalogue.
- `:508` replying is refused before held. `:517` a finished task (complete or aborted) in an unheld chat is idle and writable.
- `:1070` `test_app_refuses_to_close_while_a_chat_nobody_holds_has_an_unfinished_task`: `ChatReplying`, no `quit` call, app still running, note in catalogue.
- Changed an existing test: `:685` `test_a_chat_that_changed_after_the_receipt_was_prepared_is_not_written` appended only a `task_started` and expected `ChatChanged`. That is now correctly `ChatReplying`, so it appends a start and a completion (changed but idle) and keeps its meaning.

**Revert check**
- `replying` back to `held and unfinished`: the `:491` test and the `:1070` test fail (2 failures).
- `close()` back to scanning held chats only: the `:1070` test fails (1 failure).
- Restored; files identical to the working copies.

**User-visible change:** Codex refuses writes (`ChatReplying`) and refuses to close the app when any chat in scope has a task started without a completion, even if Baton sees no lock. Status shows such a chat as replying and not open.

## H2 — the lease path no longer skips the reply check

**Changed:** `baton/adapters/codex/writer.py:83-90` `_check`: after `lease.check()` it falls through to the replying check. The held check runs only when there is no lease, because the lease is itself an exclusive flock on the chat's lock file and would always read as held.

**Test:** `tests/adapters/test_codex.py:524` `test_an_unfinished_task_is_refused_under_the_exclusive_lease_too`. It takes a real fixture lease, sets `writer.lease`, shows `_check` passes for an idle chat (the lease's own lock is not a reason to refuse), then appends a start and expects `ChatReplying`. A whole-write version is not possible: a reply that starts after `prepare` changes the rollout, and `add` runs the unleased `_check` first and refuses there, so the lease branch can only be reached directly.

**Revert check:** put `return` back after `lease.check()`: the `:524` test fails (1 failure). Restored.

**User-visible change:** none beyond H1 (this is the race window between preflight and write).

## H3 — a root fences the adapters

**Design.** Adapters are inert by default; only the default home asks for the real ones. The decision is made once in `wiring.build`.
- `baton/cli/wiring.py:70` `is_sandboxed(explicit_root, tools_home, adapter_roots, environ)`: true for a root argument, BATON_HOME, `tools_home`, `adapter_roots` (even empty) or a non-empty BATON_TOOLS_HOME. Called once, at line 241. `Engine.sandboxed` (line 114, additive field) records it.
- `wiring.py:183` `load_adapters(..., *, sandboxed=True)`: sandboxed builds each adapter from its root alone. Only `sandboxed=False` uses the class's `on_this_machine(root)`, falling back to the plain constructor if the class has none.
- `wiring.py:84` `root_probe` and `baton/cli/tools.py:57` `installed_in`: with a sandbox, "installed" means the tool's own folder exists inside its root (new `ToolEntry.marker`, additive: `.claude`, `.codex`, `.local/share/opencode`, `.cursor`). The real `installed` (PATH and /Applications) is used only outside the sandbox. A probe passed to `build` still wins (the contract tests rely on this). `build`'s `installation_probe` default changed from `installed` to `None`.
- Adapters: `ClaudeAdapter(root)` and `CodexAdapter(root)` with no `process`/`command` now get `InertProcess` (`claude/app.py:57`, `codex/app.py:48`: sees no app or session, `alive`/`owns_session` false, `started_at` empty, open/quit/terminate raise `NotAvailable`) and `InertRunner` (`claude/runner.py:7`, `codex/runner.py:15`: never available with note `setup.runner`, `ask` raises `NotAvailable`). `on_this_machine` (`claude/tool.py:35`, `codex/tool.py:53`) passes the real `SystemProcess()` and `subprocess.run`; explicit options override. Constructing with explicit fakes works as before.

**Tests**
- `tests/unit/test_wiring_sandbox.py` (9 tests): decision matrix; `build` is sandboxed and inert for a root argument, BATON_HOME, BATON_HOME plus BATON_TOOLS_HOME, `tools_home`, per-tool roots; `load_adapters` default is inert; plain adapter classes still build either way; the default home (patched `Path.home`, `environ={}`) selects `SystemProcess` and the real runner types and the real probe, without calling any of them; an empty root reports every tool not installed; a tool folder inside the root reports installed; a passed probe wins; `main` with BATON_HOME (with and without BATON_TOOLS_HOME) runs `setup`, `chats` (both tools), `links`, `status` under the no-process guard, and `setup` shows every tool not installed and not ready, runner findings not ok.
- `tests/adapters/test_codex.py:1116` and `tests/adapters/test_claude.py:343` (3 tests each): the adapter built with only a root starts nothing, opens and quits nothing, reports no app, runner unavailable, and refuses `ask`/`open`/`close`; Claude does not treat this test's own live pid in a `.claude/sessions` file as a holder; `on_this_machine` selects the real types (types only, never called) and lets options override.

## Open questions
1. **Crashed task in a closed chat (decision needed after the live run).** A Codex chat whose newest task event is a `task_started` with no completion (the app crashed or was killed mid-reply) now refuses every Baton write and refuses automatic app closure, with the note `relaunch.replying`. Nothing Baton can do clears it. After the live run, decide whether hold detection is trustworthy enough to go back to "replying only while held", or whether a stale-start rule is needed (for example a start older than some limit, or a start from before the app's launch time).
2. **Wording.** `relaunch.replying` reads `{tool} is replying in "{title}". Closing now stops that reply.` with Wait/Close anyway buttons. It is a catalogue note, as asked, but the wording is about closing, not writing, and an adapter error carries no `title`. A write-specific note would be an additive catalogue change for E12; not made here.
3. **Same effect elsewhere.** A linked Codex chat with a crashed task now stays "replying": delivery and plans for it refuse, and the refresh marks its last turn as in progress. This follows from H1, not an extra change.
4. **Setup version on an empty root.** `setup` still prints a `version` for a not-installed tool (Claude `2.1.284`, from `facts.checked_versions`, not from the machine). It comes from a constant, not from the real machine, so H3 holds, but `SetupRead` (services) is out of scope. Consider `null` when not installed.
5. **Marker folders** for OpenCode (`.local/share/opencode`) and Cursor (`.cursor`) are the paths in the project notes; their adapters do not exist yet.
