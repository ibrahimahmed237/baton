## Step 1 — G2, one check command

**Built.** `app/scripts/check.sh` (executable, `set -euo pipefail`). It first compiles a tiny SwiftUI file (with `@State`) with the plain toolchain. If that works, it runs plain `swift build` and `swift test`. If not, it tries the SDKs under `/Library/Developer/CommandLineTools/SDKs`, newest first, uses the first that compiles it as `SDKROOT`, and adds `-Xswiftc -plugin-path -Xswiftc …/plugins/testing` to `swift test` if that directory exists. Extra arguments go to `swift test` (for example `--filter Name`). A user-set `SDKROOT` skips the search. Exit code is non-zero on any build/test failure.

**Decision where the plan was silent.** "Newest SDK" is not enough on this Mac: the newest (`MacOSX27.0.sdk`, also the default) is the one that fails (`SwiftUIMacros` plugin not found). The newest SDK that compiles SwiftUI is 26.5, so the script probes instead of trusting version order. The probe is a quick typecheck, not a full build, so a failing plain build is not paid for. I could not probe `Testing` with `swiftc` directly (it needs the framework paths that `swift test` adds), so the testing plugin path is added whenever the fallback is used.

**README.** Title "Baton app", build/test via the script, why the fallback exists, and the FixtureEngine variant-routing sentence that was out of date.

**Files.** `app/scripts/check.sh` (new), `app/README.md`, `app/Package.swift` (added `"scripts"` to the Baton executable target's `exclude`; without it SwiftPM warned about an unhandled file).

## Step 2 — G3, the failing menu-mark test

**Cause.** The product was not wrong; the test's sampling was. Rendering the menu mark through `ImageRenderer` produces correct sRGB bytes: I rendered the gradient and read the bytes back through an sRGB bitmap context, and its channel spread is at most 12/255 = 0.047, the cool tint built into `Theme.menuGlass` (stop `0x777c83` is the widest). The test instead read pixels with `NSBitmapImageRep(data: image.tiffRepresentation).colorAt(...).usingColorSpace(.deviceRGB)`. On this macOS (Darwin 27) the TIFF round trip comes back as an untagged `NSCalibratedRGBColorSpace` colour, and converting that to device RGB shifts the values (the same pixel is 0.228/0.252/0.280 raw but 0.293/0.321/0.351 after conversion), which stretches the 12-step tint to about 15 steps (0.0579 against the limit of 0.055). I cannot show that older macOS behaved differently, only that this one does and that the raw bytes are fine.

**Fix.** The test now draws the menu image into an 8-bit sRGB context and measures those bytes (helper `srgbBytes(of:)`), unpremultiplying for pixels with alpha 0.95 or more. The limit is `menuTintLimit = 15/255`, derived as the palette's widest stop (12 steps) plus 3 steps of rounding from premultiplied bytes, not a number picked to pass. The earlier limit of 0.055 equals 14/255, which is also one step of rounding away from a legitimate pixel (I observed 14/255 at pixel (5, 13) with exact sRGB bytes), so it was too tight in any colour path.

**Not changed, for Ibrahim to decide.** The mark is slightly cool, not zero-chroma. If "no colour at all" is wanted, make the three `menuGlass` stops per theme R=G=B (a one-line change in `Theme.swift`), then the test limit could drop to 3/255.

**Files.** `app/Tests/BatonUITests/BrandTests.swift`. Result: 96 of 96 pass.

## Step 3 — D6, what-will-happen and confirmation

**Built.** `PlanReviewViewModel` and `PlanReviewView` in `app/Sources/BatonUI/Screens/PlanReview/`.

- `PlanRequest` covers every plan-returning command the screens use now: link, copy, unlink, sync, continue, relaunch, brief. It runs as a preview or as the confirmation of a previewed plan and returns `ReviewedPlan` (the plan plus `replying`, `brief`, `opened`). Merge, undo, restore, rename and ask-add belong to D8 to D10 and are not wired.
- The screen shows the heading from the engine's `dialog.what_will_happen` label (from `setup().notes`), the replying chats (names as data), `PlanSteps` (close red, write green, reopen blue), and the plan's notes and offered buttons through the existing `ConfirmBar`.
- Gate: `canConfirm` needs a plan that is not applied, has no decision pending, and whose exact notes (plan notes then step notes, duplicates removed) were reported with `didDisplay(_:)`. A different, partial, or empty set never unlocks it, and a plan with no notes can never be confirmed. Every choice except Cancel goes through the gate, including rerouting to another preview. A new preview resets the gate. The view reports the notes when they appear (`onAppear` and `onChange`).
- Offers routed by the note's own button ids (labels untouched):
  - `close_sync_reopen`, `relaunch`: preview `relaunch --tool T [--then-sync L]`, then confirm that plan. This is the plan the user confirms next, gated again.
  - `sync_relaunch_later`, `add_now`: preview `sync --link L --to T`.
  - `when_idle`: preview `relaunch --when-idle`, gated again with its own notes (T6).
  - `close_anyway`, `confirm`, or an unknown id: confirm the plan on screen.
  - `attach`: nothing is sent; the outcome is `attachedInstead` (turns stay attached to the next message).
  - `cancel`: no engine call. If no note offers Cancel, the engine's `dialog.actions` Cancel label is used.
- Hand-made fixtures, one per notes-table row that has buttons or is "ordinary" (`app/Fixtures/<command>.d6_<state>.json`): `link.d6_new_chat_claude`, `link.d6_new_chat_cursor`, `link.d6_new_chat_codex`, `sync.d6_cursor_running`, `sync.d6_codex_holding`, `sync.d6_claude_open_idle`, `sync.d6_claude_replying`, `sync.d6_opencode_any_time`, `relaunch.d6_idle`, `relaunch.d6_replying` (two replying chats, one warning note per chat naming it, plus "Wait until it has finished"), `relaunch.d6_when_idle`. Note texts and button labels copy the catalogue and the notes table; the unlock states are `confirm` buttons I added where the catalogue has none (see open questions).
- Undo rows (D9) and the setup row (D11) are left to their own packages.

**Tests** (`PlanReviewTests`, 9): every state shows notes and cannot be confirmed (all choices refused, no `--confirm` reaches the engine); stale, empty and partial display never unlock; confirm sends exactly `--confirm <planID>` once; a plan with no notes is never confirmable; a new preview resets the gate; offers are named by the engine and routed (close-sync-reopen goes to a relaunch preview, attach writes nothing, add-now confirms a sync); the replying warning names both chats and "when idle" re-previews with `--when-idle` and needs its own display; cancel never writes; all states render in both themes. I mutated `canConfirm` to ignore the gate and 40+ expectations failed, then restored it.

## Open questions

- **Confirm button for ordinary plans.** Catalogue notes such as `new_chat.at_once` and `write.any_time` carry no buttons, so a plan with nothing unusual has nothing to press. The fixtures put a `confirm` button (and `cancel`) on the note; the engine must do the same (or add an additive `Plan.confirm: NoteButton`, my preference).
- **What does "Attach instead" send?** The app treats it as "write nothing, turns stay attached to the next message". If the engine needs to record the choice there is no command or flag for it.
- **Which command does "Close X, sync, reopen" run when there is no link yet** (new chat from the link dialog)? The app previews `relaunch --tool T` with no `--then-sync`; the engine must make that create the chat too, or the link flow needs its own flag.
- **`when_idle` has two meanings** (relaunch when idle; sync when the reply has finished). Both route to `relaunch --when-idle`; the second may need `sync --when-idle`.
- **Offer note values.** The engine's `limit.offer_*` notes use `time` and `other_tool`; the app's time formatting replaces only `at`, `since`, `resets_at`, so the engine's pre-formatted time shows as supplied (acceptable) or `time` must be added to `DisplayTime`.
- Setup fixtures are reused through per-command state overrides (`setup.d5_claude` for D6, `setup.d7_labels` for D7), not copied.
