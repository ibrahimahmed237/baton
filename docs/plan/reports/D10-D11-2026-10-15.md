## What was built

**D10.** A second-opinion view and model show the selected turn's messages, editable question, engine token/read-only disclosure, asynchronous status, answer and separate addition review. Generation uses `ask --chat … --background --dry-run`, then the exact confirmed token, polls `--status`, and preserves the engine's Cancel label for a pending run. Addition uses the actual `ask add` sub-command, never an immediate ask alias. A completed answer must appear before an add preview can be requested; both its exact text/identity and the add plan's current notes must then appear before confirmation. Tokens are consumed once. A changed question, stale receipt, mismatched answer, wrong destination, unexpected add step, unavailable plan, cancelled run or deadline cannot confirm.

**D11.** Setup presents four tool cards with engine findings, fixes and status colours. Trust approval, reinstalling and signing in remain instructions to the user. Installation is only eligible when a current failing hooks finding actually supplies an install control, the tool is installed, and its exact current notes have appeared. Its immediate transport sends neither dry-run nor confirm. The current engine registers no `setup install`, and current setup findings supply no install button, so no installation is offered on these generated states.

Settings read and write through `settings get/set`, including theme and glass. The settings screen resolves its palette from the engine theme plus the injected system appearance. It neither calls the local preference save methods nor uses their saved theme/glass as setting values. Every write requires the exact current display receipt. Restore defaults is a sequence of engine writes; each next write waits for the newly returned state to appear, and failure stops the sequence. Set receipts may contain only a save note; existing engine labels/defaults remain available. Setup is linked from Settings using the existing engine `screen.setup` label supplied by its window host.

`AskResult` now decodes the additive `answer_id` and accepts missing notes in retained answers. `OpinionResponse` decodes preview/add plans, job identity/state/deadline/expiry, retained answers and nested failures. A typed `Capabilities` projection exposes all documented fields while preserving the existing setup facts map and initializer compatibility.

## Decisions where the plan was silent

- Used the implemented staged `--chat` route so token/read-only consent precedes background work; kept the frozen immediate `--from` API unchanged. This follows the C5/C6 report's proposed additions.
- The view requests an add preview after the answer appears, then displays the separate add review. Only its explicit Add button can write. Copy through text selection is available; separate answer action labels remain an engine gap below.
- Reused engine-generated generic failure/empty wording from packaged fixtures for transport failures and initial empty screens. `SetupPresentation` finds executable resource bundles and the repository fixture directory; it does not create prose. Engine command errors retain their own notes. Empty states say the existing engine "No items yet" or "Choose a chat"; the generic failure says what went wrong and where details are kept.
- Kept typed capabilities additive instead of breaking existing clients of the facts dictionary. An absent/unimplemented facts map yields optional typed fields, not fabricated capabilities.
- Default restoration waits for a receipt between writes rather than applying multiple writes after the setting/choice displayed on screen has changed.
- Cancel on an unapplied second-opinion review clears the local review/answer; retained engine answers still expire by the engine's one-hour policy. Pending-run Cancel calls the engine cancel route.
